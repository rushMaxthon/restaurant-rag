# Mobile Performance Audit

Audit of `mobile/` (React Native 0.85, React 19.2, React Navigation 7). This document is the tracking sheet — each issue moves `PENDING → IN PROGRESS → DONE → VERIFIED` as we work through it.

- **Audited:** 2026-08-11
- **Scope:** `mobile/src/**` — store, navigation, screens, components, services
- **Method:** static read of every screen/component with `useEffect` / `useFocusEffect` / context consumption, plus every `api.*` call site
- **Phase 1 (API duplication + fetch loops):** complete and `VERIFIED` — 33 issues, see §5. Line references below point at the pre-Phase-1 code and may have shifted.
- **Phase 2 (re-renders, store split, L-10, A-24):** complete and `VERIFIED` — 21 issues, see §6.
- **Phase 3 (CartScreen decomposition, remaining inline rows):** complete, `DONE` — see §7. Not yet device-verified.
- **Verification:** manual testing on Android and iOS on 2026-08-11 covered Phases 1–2 and found no noticeable performance issues or behaviour regressions. See §8 for exactly what that covered — and what it did not.

## 1. Root cause summary

Three structural causes generate most of the individual issues below.

| #    | Root cause                                                                                                                                                                                                                                       | Where                                                               | Downstream issues                              |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------- | ---------------------------------------------- |
| RC-1 | **One monolithic context** holds 18 state fields + 26 callbacks in a single memoized object. Any state change — a toast, a cart quantity tap, a favorite pending flag — produces a new context value and re-renders _every_ consumer in the app. | [AppStore.tsx:1443-1538](mobile/src/store/AppStore.tsx#L1443-L1538) | R-01…R-07, A-16, A-17                          |
| RC-2 | **Effects keyed on object identity** (`preferences`, `user`, `restaurant`, `cart.items`) rather than on stable scalar keys. A parent re-render that replaces an object re-fires the effect and its API calls.                                    | multiple                                                            | A-01, A-02, A-04, A-06, A-07, A-08, A-16, A-18 |
| RC-3 | **No request cache or in-flight dedupe** in the API layer — every screen fetches independently, and the same endpoint is hit by up to 4 screens per session.                                                                                     | [api.ts:117](mobile/src/services/api.ts#L117)                       | A-05, A-13, A-14, A-22                         |

## 6. Phase 2 — what was changed

Rendering only. No API behaviour, request shape, or UI change.

### The store split (R-01…R-07)

`AppStore` published one memoized object holding 18 state fields and 26 callbacks, so a toast re-rendered every screen in the app. It now publishes **ten narrow contexts** plus a stable actions context ([AppStore.tsx](mobile/src/store/AppStore.tsx)):

| Context | Holds | Re-renders on |
| --- | --- | --- |
| `AppStoreActionsContext` | all 27 callbacks | **never** — every action is identity-stable |
| `SessionContext` | `bootstrapped`, `appConfig`, `token`, `user` | login, logout, profile change |
| `PreferencesContext` | `preferences`, `preferencesOnboardingCompleted` | preference save |
| `CartContext` | `cart` | cart mutation |
| `FavoritesContext` | the four favourite fields | favourite toggle |
| `ToastsContext` | `toasts` | toast push/expiry |
| `PromptsContext` | cart-replacement / offer prompts | prompt open/close |
| `ThemePreferenceContext`, `SelectedLocationContext`, `SelectedOfferContext`, `ChatSessionContext` | one value each | that value only |

Actions became stable by reading current state through `useLatestRef` instead of closing over it, so `setSession`, `savePreferences`, `toggleFavorite`, `performAddToCart`, `confirmCartReplacement` and the offer-prompt trio no longer change identity (R-06). New hooks in [useAppStore.ts](mobile/src/hooks/useAppStore.ts): `useAppActions`, `useSession`, `usePreferences`, `useCart`, `useFavoritesState`, `usePrompts`, `useToasts`, `useThemePreference`, `useSelectedLocation`, `useSelectedOffer`, `useChatSession`. All **26 consumers** were migrated to the narrow hooks; the composite `useAppStore()` remains for compatibility but is now unused.

`AppNavigator` no longer reads toasts or prompts — they moved into [AppOverlays.tsx](mobile/src/components/AppOverlays.tsx), rendered beside the navigator (R-05). `AppThemeProvider` now reads only `useThemePreference()` (R-07).

## 8. Verification record

**2026-08-11 — manual testing on Android and iOS. Result: no noticeable performance issues, no behaviour regressions in the tested flows.** All 54 issues moved `DONE` → `VERIFIED` on this basis.

**This pass covered Phases 1 and 2 only.** Phase 3 (§7) landed afterwards and has not yet been exercised on a device.

### What this establishes

- Both phases ship without user-visible regressions on real hardware. The Phase 1 caching, the effect re-keying, the store split, the memoization and the `onPress(item)` prop changes all behave correctly in the app.
- The flows most at risk from these changes — restaurant menu and branch switching, cart quantity and offer application, favourites, profile and saved addresses, search — behave as they did before.

### What it does not establish

Worth being precise, so nobody later reads this as more than it is:

- **No profiler traces or render counts were captured.** The before/after re-render figures in §6 remain derived from the code, not measured. "No perceptible slowdown" confirms nothing got worse; it does not independently confirm each count.
- **No network request counts were captured.** The §5 before/after figures likewise remain derived. The `requestCache` semantics themselves *are* machine-verified by [requestCache.test.ts](mobile/src/services/requestCache.test.ts) (8 tests: in-flight sharing, TTL reuse and expiry, `ttl: 0`, error non-caching, prefix invalidation, token scoping).
- **Cache-expiry edges were unlikely to be hit by hand.** The 10–30 s TTLs mean a manual pass mostly exercises cache hits. Staleness behaviour at TTL boundaries, and cross-account isolation after logout/login, are the areas least covered by this testing.
- **Low-traffic surfaces** listed under §6 "Not done" were not the focus of the pass.

### Suggested next verification

1. **A cart pass on device for Phase 3** — mode switching, scheduled slots, offer apply/remove, upsell add, quantity edits, notes, checkout. This is the one that is actually outstanding.
2. React DevTools Profiler on Home and Restaurant while tapping cart quantities — confirms the R-01…R-05 re-render claims directly.
