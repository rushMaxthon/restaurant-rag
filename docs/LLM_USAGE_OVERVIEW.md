# LLM Usage Overview

This file explains where AI/LLM is currently used in the project, where it is not used, and how the current RAG pipeline works at a high level.

## 1. AI Chat Assistant

### Where it is used
- `frontend-customer` chat
- `mobile` chat
- backend chat endpoints and RAG services

### Purpose
- answer food-related questions
- guide menu discovery
- return grounded dish and restaurant suggestions

### Current RAG flow
1. User sends a query.
2. Backend receives it through FastAPI.
3. Backend loads session context, preferences, and recent conversation state.
4. Backend tries lightweight intent parsing first for simple queries.
5. Backend performs keyword and/or vector retrieval on menu data.
6. Backend builds grounded context from relevant menu items.
7. Qwen generates the final natural-language reply when needed.
8. Backend returns reply text plus suggestion cards.

### Typical examples
- Greetings:
  - `hi`
  - `hello`
- Food recommendations:
  - `suggest something tasty`
- Food under budget:
  - `food under ₹300`
- Cuisine suggestions:
  - `show Chinese dishes`
- Alternative suggestions:
  - `burger is unavailable, show something similar`

### Input
- user message
- session/chat context
- preferences
- retrieved menu items and restaurant context

### Output
- conversational response
- grounded recommendation cards
- fallback alternatives when needed

## 2. Personalized Recommendations

### Where it is used
- Home screen `Personalized Picks`
- recommendation-backed discovery surfaces

### Purpose
- rank menu items more intelligently than simple popularity sorting

### High-level signals
- user preferences:
  - cuisines
  - favorite items
  - diet
  - spice level
  - budget
- order history:
  - repeated items
  - cuisine affinity
  - category affinity
- menu metadata:
  - availability
  - popularity
  - bestseller state
  - new-item signals

### High-level ranking behavior
- preferences are the strongest signal
- order history adds personalized reinforcement
- cuisine/category alignment improves relevance
- popularity and bestseller signals support fallback ranking
- availability and branch state still gate final output

## 3. Food Discovery / Natural Language Search

### Purpose
- turn free-form food language into structured recommendation intent

### Example queries
- `spicy veg food`
- `Chinese dishes`
- `food under ₹300`
- `healthy food options`

### How it works
- backend interprets the natural-language query
- extracts useful constraints such as:
  - cuisine
  - budget
  - diet
  - spice preference
  - category/topic
- applies retrieval and ranking using those constraints
- returns relevant dishes/restaurants instead of plain keyword matches only

### Input
- natural-language food query
- menu data
- optional user context/preferences

### Output
- ranked dishes
- matching restaurants
- refined recommendations based on extracted intent

## 4. Alternative Item Suggestions

### When it is used
- requested item is unavailable
- exact match is weak or missing
- user asks for something similar

### How it works
- backend keeps the requested topic or item intent
- finds nearby available alternatives using retrieval and ranking
- returns substitutes with grounded explanation

### Input
- requested item/topic
- availability state
- similar retrieved items

### Output
- alternative dish suggestions
- conversational explanation of substitutes

## 5. AI Offer Generation

### Where it is used
- backend daily offer-generation cron
- admin-triggered AI offer generation for local/debug use
- Home / Cart personalized offer surfaces through persisted generated offers

### Purpose
- generate personalized offer copy and bounded discount proposals from user behavior
- precompute offer cards before the customer opens the app

### Important split
- first-order welcome offers are not generated by the LLM
- new users receive one reusable deterministic `WELCOME_FIRST_ORDER` offer
- AI offer generation begins only after the customer has at least one paid order

### Input
- compact user context:
  - order history summary
  - repeated items
  - favorite restaurant or cuisine
  - inactivity state
  - preference signals
- safe backend constraints:
  - max flat discount
  - max percentage discount
  - minimum order threshold
  - validity window

### Output
- strict JSON offer proposal:
  - title
  - subtitle
  - discount type
  - discount value
  - minimum order
  - CTA
  - reason

### Safety model
- the LLM can propose content and bounded economics
- the backend validates every field before persistence
- duplicate prevention skips users who already have a fresh active AI offer
- checkout still revalidates scope, eligibility, and discount application
- if the LLM fails or returns unsafe output, the backend falls back to a deterministic safe offer

### Runtime flow
- new user registration:
  - backend attaches the reusable welcome offer immediately
  - no Qwen/Ollama call is made
- scheduled generation runs through Celery Beat
- admins can also queue the same Celery task manually from the Offers screen
- both paths reuse the same backend generation service and persistence flow

## 6. Current AI / RAG Architecture

### Stack
- FastAPI
- Ollama
- Qwen
- PostgreSQL
- pgvector
- Redis
- Embeddings
- Retrieval
- Context injection

### Simple flow

```text
User Query
  ↓
Embedding / Query Understanding
  ↓
Vector + Keyword Search
  ↓
Relevant Menu Items
  ↓
Context Injection
  ↓
Qwen
  ↓
Response
```

### Practical note
- the backend is the controller
- the LLM is not allowed to directly query PostgreSQL
- business rules and availability checks stay backend-controlled
