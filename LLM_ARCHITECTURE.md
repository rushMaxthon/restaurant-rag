# LLM Architecture

This document explains how AI and LLM-powered features work across the full Restaurant RAG project.

It is intended for:

- backend developers
- frontend and mobile developers
- product owners
- QA engineers
- future contributors onboarding into the AI stack

---

## 1. Overview

### Which LLM is being used

The project currently uses:

- `qwen3:8b` for chat-oriented language generation and intent extraction
- `nomic-embed-text` for text embeddings used in retrieval
- `Ollama` as the local inference runtime/API layer

### Why Qwen + Ollama was selected

This stack works well for a food-ordering product because it gives:

- local inference instead of sending customer chat data to a hosted third-party API
- low operational cost for development and internal deployments
- fast iteration on prompts and retrieval behavior
- predictable domain control, because the backend still owns business logic
- a good balance between quality and infrastructure simplicity

### Ollama vs Qwen

These are not the same thing:

- `Qwen` is the language model family
- `Ollama` is the runtime/server that hosts and serves the model locally

Simple mental model:

```text
Application code
  -> Ollama HTTP API
      -> Qwen model for text generation
      -> nomic-embed-text model for embeddings
```

### Local inference architecture

The backend talks to Ollama over HTTP.

Configured values today:

- Ollama base URL: `http://localhost:11434`
- Chat model: `qwen3:8b`
- Embedding model: `nomic-embed-text`

## 2. Complete LLM Usage Across Project

This section is intentionally split into two groups:

- **Direct LLM usage**: the model is actually called
- **LLM-adjacent intelligence**: the feature feels “AI-like” but is currently deterministic backend logic

### 2.1 Direct LLM usage today

#### AI Concierge chat

Primary file:

- [backend/app/services/rag.py](/Users/imac/Desktop/restaurant-rag/backend/app/services/rag.py)

The LLM is used for:

- structured intent extraction when the lightweight parser is not enough
- grounded natural-language reply generation
- conversational phrasing over backend-provided menu context
- streaming token responses for the chat UI

This is the main production LLM surface in the project.

#### Restaurant/menu Q&A

This is part of the same AI Concierge flow.

Examples:

- “Suggest spicy food”
- “Dinner under ₹20”
- “Do you have pizza?”
- “What’s new?”
- “Any new Italian dishes?”

The backend retrieves real menu data first, then Qwen formats the final answer when needed.

#### Intent-aware conversational flow

Also inside the chat system.

The LLM helps only when the backend’s fast parser is not confident enough.

Intent categories currently supported include:

- greeting
- small_talk
- dish_recommendation
- restaurant_list
- recommendation
- offer_query
- order_history
- unsupported_domain
- invalid_input
- show_more

#### Natural-language response formatting

The backend decides *what* to say.
The LLM helps decide *how to say it naturally*.

Examples:

- presenting retrieved dishes in a conversational tone
- converting structured menu context into short helpful copy
- phrasing a recommendation without exposing raw DB fields

#### Embedding generation for retrieval

File:

- [backend/app/tasks/embed.py](/Users/imac/Desktop/restaurant-rag/backend/app/tasks/embed.py)

This is not a chat-generation use case, but it is still model usage.

The embedding model is used to:

- embed menu items into vectors
- support pgvector similarity search
- improve semantic retrieval beyond plain keyword matching

Current state:

## 3. Backend vs LLM Responsibilities

This is the most important architectural rule in the project.

### What the backend controls

The backend is the decision-maker.

It controls:

- intent detection and routing
- domain boundaries
- unsupported-question handling
- greeting/acknowledgement shortcuts
- retrieval strategy
- keyword-first matching
- pgvector search
- menu filtering
- recommendation ranking
- personalization rules
- new-item logic
- combo mining
- offer eligibility
- order-history interpretation
- budget enforcement
- cart logic
- offer application rules
- safety fallbacks
- cache behavior
- chat persistence

### What the LLM controls

The LLM is the wording layer.

It controls:

- conversational tone
- short natural responses
- recommendation phrasing
- human-friendly answer formatting
- grounded explanation wording
- response fluency when backend context is already known

### Architectural principle

```text
Backend decides:
  what is valid
  what is relevant
  what can be shown

LLM decides:
  how to phrase the answer naturally
```

This separation is what keeps the assistant useful and safe.

## 4. RAG Flow

### High-level flow

```text
User Query
  -> Intent Detection
  -> Retrieval Routing
  -> Context Building
  -> LLM Prompt
  -> LLM Response
  -> Structured UI Response
```

### Detailed flow

```text
User message
  |
  v
FastAPI chat endpoint
  |
  v
Auth + session resolution
  |
  v
Fast backend checks
  - greeting?
  - acknowledgement?
  - unsupported / invalid / small talk?
  |
  v
Intent extraction
  - lightweight parser first
  - Qwen JSON extraction only when needed
  |
  v
Session state merge
  - previous topic
  - prior filters
  - follow-up context
  |
  v
Retrieval routing
  - combo path
  - new-item path
  - keyword-first path
  - embedding + pgvector path
  |
  v
Business filtering
  - availability
  - approved restaurant
  - active location
  - budget
  - diet
  - follow-up exclusions
  |
  v
Safe context block
  |
  v
Qwen final reply generation when needed
  |
  v
Reply validation
  |
  v
Persist chat history + return suggestions
```

### Structured UI response

The LLM response is never the whole product output.

The chat API returns:

- `reply`
- `session_id`
- `suggestions[]`

That means frontend and mobile can render:

- natural assistant text
- structured suggestion cards
- add-to-cart actions
- favorites
- item detail navigation

## 5. Prompt Engineering

### System prompt

The main system prompt tells the model:

- it is a food ordering assistant
- it must use only backend-provided menu context
- it must never invent items, prices, restaurants, or availability
- it should keep answers short and recommendation-focused

This is the core anti-hallucination rule.

### Intent prompt

The intent prompt is JSON-only.

Its job is not to be creative.
Its job is to classify requests into structured routing fields.

Examples of extracted fields:

- intent
- dish
- cuisine
- category
- restaurant_query
- budget
- diet
- spicy
- mood
- new_only

### Recommendation prompt

The recommendation prompt receives:

- structured intent
- session summary
- recent history
- grounded menu context
- user question

This lets the model sound natural without inventing business logic.

### Safety / fallback prompt behavior

The backend often bypasses the LLM entirely when:

- greeting can be instant
- acknowledgement can be instant
- keyword matches are already safe enough
- unsupported-domain query should be redirected
- no-candidate fallback should be deterministic

This is intentional.

### Non-food redirect behavior

For unrelated questions, the assistant now does not continue into menu retrieval.

Instead it returns a polite domain-safe redirect such as:

```text
I'm mainly designed to help with food, restaurants, menus, offers, and meal recommendations.
You can ask things like spicy food, dinner under a budget, healthy meals, or the best combos near you.
```

That is a backend-controlled conversation boundary.

## 6. Safety + Domain Boundaries

### How unrelated questions are handled

Examples:

- “Do you know Narendra Modi?”
- “What is IPL?”
- “Who is Elon Musk?”

These are classified as `unsupported_domain`.

Behavior:

- no food retrieval
- no random fallback dishes
- no hallucinated general knowledge answer
- polite redirect back to restaurant help

### How hallucinations are reduced

The project reduces hallucination risk through architecture, not just prompting.

Key methods:

- backend retrieval happens before generation
- LLM never queries the DB directly
- only backend-approved candidates enter the context block
- unsupported queries short-circuit before retrieval
- deterministic fallback replies replace generic low-value model output
- contradictory unavailable-item replies are intercepted and corrected

### Why the assistant stays restaurant-focused

Because the backend enforces:

- supported intents
- grounded context only
- safe fallback wording
- zero-suggestion unsupported paths

This creates a domain-bounded concierge rather than a generic chatbot.

## 7. Personalization Flow

Personalization is mostly backend intelligence, with the LLM only formatting the final answer.

### Signals used for personalization

Current backend signals include:

- user preferences
- favorite cuisines
- favorite items
- spice preference
- dietary preference
- budget behavior
- order history
- repeated orders
- recent orders
- cuisine affinity
- category affinity
- popularity fallback
- new-item launch windows

### Personalization flow

```text
Preferences + Order History + Active Query
  -> Recommendation scoring
  -> Candidate ranking
  -> Safe suggestion list
  -> LLM wording (only if needed)
```

### How user behavior influences results

#### Order history

- repeated item orders raise affinity
- repeated cuisine orders raise cuisine match
- recent orders add recency weight
- paid orders in active lifecycle states are used

#### Favorite cuisines

- explicit preferences and top-order cuisines both matter

#### Spending habits

- average order value influences budget-aware suggestions
- high minimum-order offers may be filtered out for low-budget users

#### Repeat orders

- repeated items influence recommendations
- repeated items also influence personalized offers

#### Time-based behavior

Today this is limited compared with a full temporal ML recommender, but the system still uses:

- recency of orders
- inactivity windows for offers
- new-item launch windows
- combo lookback windows

#### Combos

- generated combos are mined from order co-occurrence
- chat can route combo queries into combo retrieval
- cart upsell and cross-sell use combo intelligence

## 8. Offer AI Flow

### Current reality

The offers system is “AI-style” in product behavior, but it is not primarily LLM-generated today.

### How offers are created

Files:

- [backend/app/services/personalized_offers.py](/Users/imac/Desktop/restaurant-rag/backend/app/services/personalized_offers.py)
- [backend/app/services/orders.py](/Users/imac/Desktop/restaurant-rag/backend/app/services/orders.py)

Offer generation is driven by:

- business-approved templates
- order insights
- repeated-order patterns
- favorite restaurant/item signals
- cuisine affinity
- inactivity windows
- combo affinity
- budget behavior

### Repeated-order offers

Example logic:

- if a user keeps ordering a favorite item
- and a matching offer template exists
- the backend scores that offer highly
- generated copy is then assembled from safe templates

### Inactive-user offers

Example logic:

- if the user has not ordered for `N` days
- and there is an inactive-user offer template
- the backend may prioritize a comeback offer

### Dynamic offer wording

Current state:

- not LLM-generated
- deterministic template-based copy
- examples include generated title/subtitle/badge/CTA fields

This is intentional because offers need:

- business safety
- predictable marketing language
- auditability
- stable conversion measurement

### Why this matters

This project treats offers as a business-critical feature.
That means copy safety and eligibility correctness are more important than creative generation.

- AI Concierge intent extraction when needed

- recommendation scoring

- combo mining
- upsell suggestions
- cross-sell logic
